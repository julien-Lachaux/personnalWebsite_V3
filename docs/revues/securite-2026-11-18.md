## RS-1 : l'API « lecture seule » se connecte en superutilisateur PostgreSQL (majeur, CONFIRMÉ)

- **Fichiers** : `docker/compose.prod.yml:38` (`DATABASE_URL` de `api` = `POSTGRES_USER`), `docker/compose.prod.yml:71-73`,
  `db/migrations/*` (aucun `create role` / `grant`).
- **Scénario** : `POSTGRES_USER` crée un rôle **superutilisateur**. L'API, qui ne fait que des `select`, détient
  donc DDL, `pg_read_server_files`, `COPY … PROGRAM`. Toute faille future côté API (RCE dans une dépendance,
  injection introduite par un futur endpoint) devient une exécution de commandes dans le conteneur PostgreSQL et
  la destruction des données, au lieu d'une simple lecture de contenu public.
- **Reproduction** (pile prod lancée) :

  ```sh
  docker exec <api> node --input-type=module -e "import postgres from 'postgres';
    const sql = postgres(process.env.DATABASE_URL, { max: 1 });
    console.log(await sql\`select current_user, (select rolsuper from pg_roles where rolname=current_user)\`);
    console.log(await sql.unsafe(\"create temp table t(x text); copy t from program 'id'; select x from t\"));
    await sql.end();"
  # → superuser: true ; x: 'uid=70(postgres) gid=70(postgres) groups=70(postgres)'
  ```
- **Proposition** : script d'init PostgreSQL (`/docker-entrypoint-initdb.d`) ou étape du service `migrate`
  créant un rôle `siteperso_api` (`login`, mot de passe distinct `API_DB_PASSWORD`) avec `grant connect`,
  `grant usage on schema public`, `grant select on all tables in schema public` et `alter default privileges
  … grant select on tables` ; `api` se connecte avec ce rôle, seul `migrate` garde le rôle propriétaire.
  Le rôle d'amorçage ne peut pas perdre `superuser` lui-même : un second rôle est nécessaire.
  Test e2e : `has_table_privilege('siteperso_api', 'profile', 'INSERT')` = false.

## RS-3 : BUG-3 cache un DoS : corps de 1 Mio parsés sur toute route inconnue, hors quota, sans limite chez Caddy ; les préflights ne sont pas comptés non plus (majeur, CONFIRMÉ)

- **Fichiers** : `apps/api/src/infrastructure/http/create-app.ts:35-46` (rate limit par `onRoute`, `bodyLimit`
  Fastify par défaut 1 048 576, CORS), `docker/Caddyfile:115-117` (aucun `request_body max_size`).
- **Scénario** : BUG-3 (lot 4) a été jugé « faible : réponse minuscule, aucun accès base ». Mais le gestionnaire
  404 de Nest s'exécute **après** l'analyse du corps : un `POST` de 1 Mio de JSON sur `/api/v1/nope` est
  entièrement lu et passé à `secure-json-parse` (≈ 20-30 ms CPU par requête), sans jamais consommer de quota.
  Un seul client dégrade tout le site. De même, les préflights `OPTIONS` (204 par `@fastify/cors`) ne portent
  aucun `x-ratelimit-*` et ne sont pas comptés.
- **Reproduction** (via Caddy, `RATE_LIMIT_MAX=100`) :

  ```sh
  python3 -c "import json;open('obj.json','w').write(json.dumps([{'k':i,'v':'x'} for i in range(50000)])[:1040000].rsplit(',',1)[0]+']')"
  for i in $(seq 150); do curl -sk -o /dev/null -w '%{http_code}\n' -X POST \
    -H 'content-type: application/json' --data-binary @obj.json https://localhost:18443/api/v1/nope; done | sort | uniq -c
  # → 150 × 404 en 5,3 s (150 Mo analysés), puis GET /health : x-ratelimit-remaining: 99
  for i in $(seq 150); do curl -sk -o /dev/null -w '%{http_code}\n' -X OPTIONS -H 'Origin: https://front.example.test' \
    -H 'Access-Control-Request-Method: GET' https://localhost:18443/api/v1/cv; done | sort | uniq -c   # → 150 × 204
  # Latence de GET /health : 10 ms au repos → 520-780 ms pendant 600 POST de 1 Mo en 16 flux parallèles,
  # et le compteur n'a décompté que les 11 GET /health.
  ```
- **Proposition** : `new FastifyAdapter({ trustProxy, bodyLimit: 1024 })` (l'API n'accepte aucun corps) ou
  hook `onRequest` qui répond 404/405 à toute méthode autre que GET/HEAD/OPTIONS avant lecture du corps ;
  rate limit `global: true` avec `app.setNotFoundHandler` passé par `rateLimit` (correctif BUG-3) ;
  dans le Caddyfile, `request_body { max_size 1KB }` sous `handle /api/*` et `@write not method GET HEAD OPTIONS`
  → `respond 405`. Test e2e : `POST` de 2 Kio → 413 sans lecture complète ; 101 préflights → 429.

## RS-4 : les clients qui passent par docker-proxy partagent une seule clé de rate limiting (majeur, PLAUSIBLE)

- **Fichiers** : `docker/compose.prod.yml:13-16` (ports publiés en IPv4 et IPv6), `docker/compose.prod.yml:94-95`
  (réseau `internal` sans `enable_ipv6`), `apps/api/src/infrastructure/http/create-app.ts:35-38` (clé = `request.ip`).
- **Scénario** : la clé du quota est l'IP vue par Caddy. Sur un réseau bridge IPv4-only, les connexions IPv6
  entrantes (et toute connexion relayée par le userland-proxy de Docker) arrivent depuis la passerelle
  `172.x.0.1` : Caddy écrit cette adresse dans `X-Forwarded-For`, et tous ces visiteurs partagent **un seul**
  quota de 100 requêtes/minute. Un client IPv6 qui envoie 100 requêtes met en 429 tous les autres visiteurs
  IPv6 pendant une minute ; du trafic légitime suffit d'ailleurs à l'atteindre. Le même effet frappera le futur
  service `web` s'il appelle l'API côté serveur (toutes les requêtes SSR depuis l'IP du conteneur `web`).
  Caddy n'a aucun journal d'accès : impossible de voir l'IP retenue en production.
- **Reproduction** (localement, sous WSL, IPv4 et IPv6 sont tous deux relayés) :

  ```sh
  docker exec <caddy> netstat -tn | grep :443        # pairs distants : ::ffff:172.26.0.1 pour -4 comme pour -6
  for i in $(seq 101); do curl -sk --resolve localhost:18443:::1 -o /dev/null -w '%{http_code}\n' \
    https://localhost:18443/api/v1/health; done | sort | uniq -c                   # 100 × 200, 1 × 429
  curl -sk --resolve localhost:18443:127.0.0.1 -D- -o /dev/null https://localhost:18443/api/v1/health
  # → HTTP/2 429, retry-after: 59 : le client IPv4 est bloqué par le client IPv6
  ```
  Sur le VPS : activer un `log` Caddy, se connecter en IPv6 et lire `remote_ip`.
- **Proposition** : `enable_ipv6: true` + sous-réseau IPv6 sur `internal` (ou `userland-proxy: false`
  côté démon) pour conserver l'IP source ; `log { output stdout }` dans le Caddyfile ; `keyGenerator` du
  rate limit qui regroupe les IPv6 par /64 ; pour le futur SSR, quota distinct ou en-tête de confiance
  dédié. Vérification post-déploiement documentée dans `docs/deploiement.md`.

## RS-5 : `TRUST_PROXY=true` fait confiance à tous les sauts : `X-Forwarded-For` falsifiable par tout client direct (mineur, CONFIRMÉ)

- **Fichiers** : `apps/api/src/infrastructure/config/env.schema.ts:33-36`, `apps/api/src/infrastructure/http/create-app.ts:27`,
  `docker-compose.yml:194-196` (profil `api` : `TRUST_PROXY: 'true'` et port publié **sans** proxy).
- **Scénario** : `trustProxy: true` retient l'adresse la plus à gauche de `X-Forwarded-For`, quel que soit
  l'émetteur. Derrière Caddy c'est sans effet (Caddy écrase l'en-tête : vérifié, trois `X-Forwarded-For`
  différents via Caddy décomptent le même quota). Mais tout client qui joint `api:3000` directement (n'importe
  quel conteneur du réseau `internal`, l'essai local du profil `api`, une future exposition par erreur) tourne
  l'en-tête et obtient un quota neuf à chaque requête.
- **Reproduction** :
  `docker exec <api> wget -qS -O /dev/null --header='X-Forwarded-For: 9.9.9.9' http://127.0.0.1:3000/api/v1/health`
  puis avec `9.9.9.8` → `x-ratelimit-remaining: 99` les deux fois (deux seaux distincts).
- **Proposition** : accepter dans `TRUST_PROXY` un nombre de sauts ou une liste CIDR (`trustProxy: 1` ou
  `'172.16.0.0/12'`) ; `TRUST_PROXY: 'false'` dans le profil `api` de `docker-compose.yml`.

## RS-6 : aucune borne de temps : une base qui ne répond plus fige toutes les requêtes, `/health` ne renvoie jamais 503 (mineur, CONFIRMÉ)

- **Fichiers** : `apps/api/src/infrastructure/db/drizzle-database-client.ts:18-22` (pas de `connect_timeout`,
  `idle_timeout`, `statement_timeout`), `apps/api/src/infrastructure/http/create-app.ts:27` (Fastify 5 :
  `requestTimeout` et `handlerTimeout` à 0), `apps/api/src/application/health/get-health.use-case.ts:10`.
- **Scénario** : base saturée, verrou, réseau coupé sans RST : chaque requête attend indéfiniment et occupe une
  connexion du pool (10) ; les requêtes s'accumulent en mémoire. Le contrôle de santé, conçu pour répondre 503,
  ne répond pas du tout ; le `HEALTHCHECK` Docker passe `unhealthy` mais `restart: unless-stopped` ne
  redémarre pas un conteneur `unhealthy`.
- **Reproduction** : `docker pause <postgres>` puis `curl --max-time 40 …/api/v1/health` et `…/cv` → `000`
  après 40 s (aucune réponse) ; `docker unpause` → 200 en 3 ms.
- **Proposition** : `postgres(url, { max: 10, connect_timeout: 5, idle_timeout: 60, connection: { statement_timeout: 5000 } })` ;
  `ping()` borné par `Promise.race` à 2 s (→ 503) ; `new FastifyAdapter({ requestTimeout: 10_000, handlerTimeout: 10_000 })`
  (Caddy reste devant pour les connexions lentes).

## RS-7 : réseau plat et conteneurs non durcis (mineur, CONFIRMÉ)

- **Fichiers** : `docker/compose.prod.yml:26-27,49-50,64-65,81-82,94-95` (un seul réseau `internal`, non
  `internal: true`), `docker/api.Dockerfile:36-40` (`--chown=node:node`), absence de `read_only`, `cap_drop`,
  `security_opt`, limites mémoire/PID dans `compose.prod.yml`.
- **Scénario** : Caddy, exposé à Internet, joint PostgreSQL sur 5432 ; l'API a une sortie Internet
  (exfiltration, téléchargement d'outils) ; le code de l'API (`dist/`) et `db/migrations` appartiennent à
  l'utilisateur d'exécution `node` et sont modifiables par lui (persistance d'une compromission tant que le
  conteneur vit) ; l'image d'exécution embarque `npm`, `npx`, `wget`, `nc`.
- **Reproduction** :
  `docker exec <caddy> nc -z -w 2 postgres 5432` → joignable ;
  `docker exec <api> wget -q -T 5 -O /dev/null https://registry.npmjs.org/` → joignable ;
  `docker run --rm --entrypoint sh siteperso-api:… -c 'touch dist/main.js /repo/db/migrations/0001_enums.sql'` → réussit ;
  `docker inspect <api>` → `ReadonlyRootfs=false CapDrop=[] SecOpt=[] Mem=0 Pids=<nil>`.
- **Proposition** : deux réseaux (`edge` : caddy + api ; `data` : api + migrate + postgres, `internal: true`) ;
  `COPY` sans `--chown` (fichiers root, lecture seule pour `node`) ; `read_only: true` + `tmpfs: /tmp`,
  `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `mem_limit`, `pids_limit` ; supprimer
  `npm`/`npx` de l'étape runtime (`rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/np*`).

## RS-8 : les contrats acceptent `javascript:`, `data:`, `mailto:`, `tel:` dans toutes les URL, et le SQL ne contraint rien (mineur, CONFIRMÉ)

- **Fichiers** : `packages/contracts/src/social-links/social-links.ts:16`, `resources/resources.ts:11`,
  `projects/projects.ts:12-13`, `tools/tools.ts:9`, `experiences/experiences.ts:23`, `education/education.ts:17`,

  des migrations 0005 à 0007 (aucun `check`).
- **Scénario** : la validation stricte des réponses est la dernière barrière avant le front. Une URL
  `javascript:` (seed erroné, copier-coller, base compromise via RS-1) passe le contrat, est servie par l'API et
  deviendra une XSS stockée dès que le front la liera dans un `href`. La garantie « aucun e-mail ni téléphone »

- **Reproduction** :

  ```sh
  node --input-type=module -e "import { SocialLinkSchema } from './packages/contracts/dist/index.js';
    console.log(SocialLinkSchema.safeParse({ slug:'x', kind:'website', url:'javascript:alert(document.domain)', label:'X' }).success)"
  # → true (idem data:text/html,…, vbscript:, mailto:, tel:)

  curl -s localhost:3532/api/v1/social-links   # → …{"slug":"xss","kind":"website","url":"javascript:alert(document.domain)",…}
  ```
- **Proposition** : `HttpUrlSchema = z.url({ protocol: /^https?$/ })` dans `common/` et utilisé partout ;
  `check (url ~ '^https?://')` sur chaque colonne d'URL (nouvelle migration) ; test e2e de non-régression.

## RS-11 : scripts d'exploitation destructeurs sans garde-fou (mineur, CONFIRMÉ)

- **Fichiers** : `scripts/deploy/backup.sh:10,34`, `scripts/deploy/update.sh:18-19`,
  `apps/api/src/infrastructure/db/reset-database.ts:16`, `docker/api.Dockerfile:37` (`dist/cli/reset.js` dans l'image).
- **Scénario** :
  1. `BACKUP_KEEP` n'est pas validé : `BACKUP_KEEP=0` (ou une faute de frappe) supprime **toutes** les
     sauvegardes, y compris celle qui vient d'être faite, et le script finit « Terminé. » en code 0.
  2. `update.sh` applique les migrations sans sauvegarde préalable.
  3. La garde de `db:reset` ne lit que `NODE_ENV` ; le script est livré dans l'image de prod et
     `-e NODE_ENV=development` suffit à recréer le schéma de la base de prod (impact limité aujourd'hui : tout
     le contenu vient des seeds, mais toute retouche manuelle serait perdue).
- **Reproduction** :

  ```sh
  DEPLOY_DIR=<tmp> COMPOSE_PROJECT_NAME=<pile> bash scripts/deploy/backup.sh               # 1 fichier
  DEPLOY_DIR=<tmp> COMPOSE_PROJECT_NAME=<pile> BACKUP_KEEP=0 bash scripts/deploy/backup.sh  # exit 0, dossier vide
  docker compose … run --rm --no-deps migrate node dist/cli/reset.js                        # refusé, exit 1
  docker compose … run --rm --no-deps -e NODE_ENV=development migrate node dist/cli/reset.js
  # → « schéma public recréé », migrations et seeds rejoués, exit 0
  ```
- **Proposition** : `[[ "${BACKUP_KEEP}" =~ ^[1-9][0-9]*$ ]] || die …` ; appel de `backup.sh` en tête de
  `update.sh` ; exclure `dist/cli/reset.js` de l'image (ou le refuser si `current_database()` ne finit pas par
  `_dev`/`_test`) ; prévoir une copie hors VPS des sauvegardes.

## RS-12 : empreinte de Caddy malgré `-Server`, pas de CSP sur la page servie (mineur, CONFIRMÉ)

- **Fichiers** : `docker/Caddyfile:106-113`.
- **Scénario** : la volonté de masquer le logiciel frontal (lot 5 : « pas d'en-tête `Server` ») n'est que
  partielle : toutes les réponses proxifiées portent `Via: 1.1 Caddy`, et la redirection HTTP → HTTPS (port 80,
  hors bloc `header`) renvoie `Server: Caddy`. Aucune `Content-Security-Policy` ni sur l'API (décision du lot 0,
  rappelée par le lot 4) ni sur la page `placeholder` : `default-src 'none'; frame-ancestors 'none'` ne coûte
  rien sur une API JSON et durcit le cas où un navigateur interpréterait une réponse.
- **Reproduction** : `curl -sk -D- -o /dev/null https://localhost:18443/api/v1/profile | grep -i via` → `via: 1.1 Caddy` ;
  `curl -s -D- -o /dev/null http://localhost:18080/api/v1/health | grep -i server` → `Server: Caddy`.
- **Proposition** : `reverse_proxy api:3000 { header_down -Via }` ; bloc global `servers { … }` ou site
  `http://` explicite avec `header -Server` ; `Content-Security-Policy "default-src 'none'; frame-ancestors 'none'"`
  sous `handle /api/*` (et une CSP adaptée pour la page statique).

  `X-Forwarded-For` correctement écrasé par Caddy, TLS 1.2 minimum, HSTS, nosniff, chemins traversants refusés.

  sous verrou consultatif avec checksum SHA-256 et transaction par fichier.
