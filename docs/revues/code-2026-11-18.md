## RC-1 : e2e dépendants de l'ordre d'exécution, job CI `e2e` rouge sur base neuve

- **Fichiers** : `apps/api/test/published-and-order.e2e-spec.ts:156`, `apps/api/test/security.e2e-spec.ts:42`
  (et `:103`), `apps/api/test/errors.e2e-spec.ts:55`, `apps/api/test/matrix.e2e-spec.ts:24`,
  `apps/api/test/openapi-conformance.e2e-spec.ts:71` ; `.github/workflows/ci.yml:68`.
- **Gravité** : bloquant.
- **Défaut** : ces cinq fichiers démarrent l'application sans appeler `resetTestDatabase()` ; ils supposent une
  base déjà migrée et seedée, laissée par un autre fichier passé avant eux. Les autres e2e la recréent dans leur
  `beforeAll`. Vitest exécute d'abord les fichiers en échec et les plus lents (cache `results.json`). Sans cache,
  il exécute d'abord les plus gros : `published-and-order` (355 lignes), `security` (328), `errors` (293). C'est la
  cause réelle du « premier `pnpm check` parfois rouge » (`relation "resources" does not exist`), qui n'est donc
  pas une instabilité.
- **Scénario de défaillance** : en CI, le service `postgres` est neuf, aucune étape ne migre la base avant
  `pnpm test:e2e`, et le runner n'a pas de cache Vitest. Les gros fichiers passent en premier sur une base vide :
  le job `e2e` est rouge à chaque push (76 échecs mesurés). Le lot 5 n'a pas pu exécuter la CI sur GitHub. En
  local, le défaut revient après chaque `docker compose down` (base de test en tmpfs).
- **Reproduction** :
  ```sh
  docker compose rm -sf postgres-test && pnpm db:test:up
  pnpm --filter @siteperso/api exec vitest run --config vitest.e2e.config.ts --no-cache
  # Tests 76 failed ; PostgresError: relation "resources" does not exist
  # relancer la même commande : vert (la base a été laissée seedée par le dernier fichier)
  ```
  Variante sur un fichier seul :
  `pnpm --filter @siteperso/api exec vitest run --config vitest.e2e.config.ts test/published-and-order.e2e-spec.ts`
  sur base neuve donne 23 échecs sur 25.
- **Proposition** : un `globalSetup` dans `vitest.e2e.config.ts` qui appelle `resetTestDatabase()` une fois, et
  `await resetTestDatabase()` dans le `beforeAll` des cinq fichiers (même convention que les e2e de ressource).
  Ajouter au job CI une deuxième exécution
  `pnpm --filter @siteperso/api exec vitest run --config vitest.e2e.config.ts --sequence.shuffle` pour détecter
  toute dépendance d'ordre restante.

## RC-3 : règle « image » divergente, un `logo_alt` vide fait tomber `/experiences` et `/cv` en 500

- **Fichiers** : `apps/api/src/application/experiences/list-experiences.use-case.ts:24-27` ;
  `apps/api/src/application/projects/list-projects.use-case.ts:10` et
  `apps/api/src/application/resources/list-resources.use-case.ts:10` (deux copies de `toImage`).
- **Gravité** : majeur.
- **Défaut** : trois implémentations de la même règle (« pas d'image sans texte alternatif »). `projects` et
  `resources` (agent B) écartent `null` et `''`. `experiences` (agent A) n'écarte que `null`. Le contrat
  `ImageSchema` impose `alt` et `path` en `min(1)`.
- **Scénario de défaillance** : une traduction saisie avec `logo_alt = ''` (ou `logo_path = ''`) passe le SQL.
  Le cas d'usage construit alors `{ path, alt: '' }`, la validation stricte du contrôleur lève une `ZodError`, et la
  route répond 500. Comme `/cv` refuse toute réponse partielle, le CV entier tombe dans cette langue. La même
  donnée vide dans un projet donne simplement `imageDesktop: null`.
- **Reproduction** :
  ```sh
  psqld -c "update experiences_translations set logo_alt = '' where locale = 'en'
            and experience_id = (select id from experiences where slug = 'nopillo')"
  curl -s -o /dev/null -w '%{http_code}\n' 'localhost:3512/api/v1/experiences?lang=en'   # 500
  curl -s -o /dev/null -w '%{http_code}\n' 'localhost:3512/api/v1/cv?lang=en'            # 500
  curl -s -o /dev/null -w '%{http_code}\n' 'localhost:3512/api/v1/experiences?lang=fr'   # 200
  ```
- **Proposition** : un seul `toImage(path, alt): Image | null` dans `apps/api/src/application/common/image.ts`
  (fonction pure, sans dépendance), utilisé par `experiences`, `projects` et `resources`, avec un test unitaire
  qui couvre `null` et `''`. Côté SQL (lot base de données), ajouter `check (logo_alt <> '')`, `check (image_alt <> '')`
  et `check (picture_alt <> '')`. `profile_translations.picture_alt` est concerné aussi : vide, il fait tomber
  `/profile` et `/cv`.

## RC-4 : seeds non convergents, une ligne retirée reste en base, une faute de slug est ignorée

- **Fichiers** : `db/seeds/0004_experiences.sql:308-352` (`experience_skills`), même motif dans
  `db/seeds/0003_skills.sql` et `0005_*.sql` ; `db/README.md` (« Idempotence obligatoire ») ;
  `docker/compose.prod.yml:57` (le service `migrate` rejoue les seeds à chaque déploiement) ;
  `apps/api/test/db/seeds.e2e-spec.ts:60` (idempotence vérifiée par comptages seulement).
- **Gravité** : majeur.
- **Défaut** : les seeds ne font que des `insert … on conflict do update`. Ils sont idempotents mais pas
  convergents : rejouer le seed n'aligne pas la base sur le fichier. Les traductions et les liaisons utilisent en
  plus `join skills s on s.slug = v.skill_slug` ou `select … from experiences p where p.slug = '…'`. Un slug mal
  orthographié ne produit donc aucune ligne et aucune erreur.
- **Scénario de défaillance** : Julien retire `('nopillo', 'mastra')` de la stack, ou supprime une traduction EN
  pour revenir au repli FR, puis déploie (`scripts/deploy/update.sh` → `migrate` → `seed.js`). La ligne reste en
  production et l'API continue de l'exposer. Le seed est le seul canal d'édition du contenu, donc le seul recours
  est un `delete` à la main en production. De même, une faute de frappe dans un slug (`'typscript'`) fait
  disparaître la compétence de l'expérience sans aucun signal : le test e2e compare des comptages avant et après
  rejeu, pas avec le fichier.
- **Reproduction** (ligne « retirée du seed » simulée par une ligne présente en base et absente du fichier) :
  ```sh
  psqld -c "insert into experience_skills (experience_id, skill_id, sort_order)
            select e.id, s.id, 99 from experiences e, skills s where e.slug = 'nopillo' and s.slug = 'php'"
  pnpm db:seed
  psqld -Atc "select count(*) from experience_skills es join experiences e on e.id = es.experience_id
              join skills s on s.id = es.skill_id where e.slug = 'nopillo' and s.slug = 'php'"   # 1
  curl -s localhost:3512/api/v1/experiences | grep -o '"slug":"php"' | head -1             # toujours exposé
  ```
- **Proposition** : pour les tables de liaison, dans la même transaction de seed, un CTE `seed(experience_slug, skill_slug, sort_order)`
  partagé par un `delete from experience_skills … where experience_id in (<expériences seedées>) and (experience_id, skill_id) not in (select … from seed join …)`
  puis par l'`insert … on conflict`. Même principe pour les traductions
  d'entités seedées. Pour les entités, décider explicitement : soit `published = false` pour tout slug absent du
  fichier, soit une suppression. Pour les fautes de slug, terminer chaque bloc par une garde
  `do $$ begin if (select count(*) from …) <> <attendu> then raise exception 'slug inconnu'; end if; end $$;`, ou
  joindre en `left join` et lever si `s.id is null`. Côté test, comparer un instantané du contenu
  (`md5(string_agg(...))` par table) avant et après rejeu, et pas seulement des comptages. SQL explicite :
  fidèle au portage Rust.

## RC-5 : `?lang` et validation de réponse recopiés dans 12 contrôleurs, `/cv` validé deux fois

- **Fichiers** : `apps/api/src/infrastructure/http/*/*.controller.ts` (12 copies du bloc `LocaleQuerySchema.safeParse`
  + `BadRequestException`) ; `apps/api/src/application/cv/get-cv.use-case.ts:72` et
  `apps/api/src/infrastructure/http/cv/cv.controller.ts:19`.
- **Gravité** : mineur.
- **Défaut** : le même bloc est recopié 12 fois, avec deux messages : 7 contrôleurs (agent A, cv) disent
  « valeurs acceptées fr, en. », 5 (agent B) disent « valeurs permises « fr » ou « en ». ». La validation de
  réponse prend trois formes (`const XResponseSchema = z.array(...)`, `Schema.array().parse(...)`, et
  `CvSchema.parse` dans le cas d'usage puis encore dans le contrôleur). La règle « validation stricte de la
  réponse » vit tantôt dans l'application, tantôt dans `http`.
- **Scénario de défaillance** : le front, ou un test de contrat Rust qui compare `detail`, voit deux textes
  différents pour la même erreur. Une évolution de `lang` (troisième langue, message) demande 12 modifications
  identiques et 12 jeux de tests unitaires (`controllers.spec.ts` les teste déjà un par un). `/cv` parse environ
  40 objets deux fois par requête, sans bénéfice.
- **Reproduction** :
  ```sh
  curl -s 'localhost:3512/api/v1/profile?lang=de'   # "detail":"… valeurs acceptées fr, en."
  curl -s 'localhost:3512/api/v1/projects?lang=de'  # "detail":"… valeurs permises « fr » ou « en »."
  grep -rh -A1 "BadRequestException(" apps/api/src/infrastructure/http/*/*.controller.ts | grep -o "valeurs [a-z]*" | sort | uniq -c
  ```
- **Proposition** : `apps/api/src/infrastructure/http/common/locale-query.ts` exportant
  `parseLocaleQuery(raw: unknown): Locale`, qui lève l'unique `BadRequestException`. C'est une fonction
  explicite, pas un pipe, donc conforme à « appel explicite de `safeParse` ». Les contrôleurs deviennent
  `return Schema.array().parse(await this.useCase.execute(parseLocaleQuery(query)))`. Retirer le `CvSchema.parse`
  du cas d'usage, ou celui du contrôleur, pour garder une seule convention : valider dans `http`, comme les 11
  autres.

## RC-6 : jointures de traduction recopiées 11 fois, typage de `translated` non vérifié

- **Fichiers** : `apps/api/src/infrastructure/db/*/drizzle-*.repository.ts` (11 × `alias` fr/en + `innerJoin(fr …)`
  + `leftJoin(en …)`) ; `apps/api/src/infrastructure/db/translated.ts:13-14` ;
  `apps/api/src/infrastructure/db/languages/drizzle-languages.repository.ts:36`.
- **Gravité** : mineur.
- **Défaut** : le motif « fr obligatoire en `inner join`, langue demandée en `left join` » est recopié dans chaque
  dépôt, avec des noms d'alias incohérents (`'fr'`/`'en'` chez B, `'profile_fr'`/`'skill_fr'` chez A). Le type de
  `translated<T = string>` est déclaré à la main : il n'est pas déduit de la nullabilité des colonnes. Oublier
  `<string | null>` sur une colonne nullable compile en `string`. Le domaine reçoit alors un `string` qui vaut
  `null` à l'exécution, et seul le `parse` Zod final le rattrape (500). `cefrLevel` est forcé par
  `as CefrLevel | null` au lieu d'être typé à la source.
- **Scénario de défaillance** : un futur dépôt écrit `location: translated(en.location, fr.location)`. Typecheck
  vert. Le cas d'usage traite `location` comme non nul, et une ligne sans lieu donne un 500 ou un `.trim()` sur
  `null`.
- **Reproduction** : dans `drizzle-experiences.repository.ts:40`, remplacer
  `translated<string | null>(en.location, fr.location)` par `translated(en.location, fr.location)`, puis lancer
  `pnpm typecheck` : vert, alors que `experiences_translations.location` est nullable (`db/migrations/0005_experiences.sql`).
- **Proposition** : typer `translated` depuis la colonne. Signature :
  `translated<C extends AnyPgColumn>(en: C, fr: C): SQL<C['_']['notNull'] extends true ? C['_']['data'] : C['_']['data'] | null>`.
  Elle supprime aussi tous les arguments de type explicites. Ajouter un petit helper
  `translationAliases(table, prefix)` qui renvoie `{ fr, en, frOn(fk, id), enOn(fk, id, locale) }`, pour un seul
  nommage et une seule écriture du repli. Le SQL rendu reste identique (test `translated.spec.ts`). Typer
  `languages.cefr_level` par `text('cefr_level', { enum: CEFR_LEVELS })` pour supprimer le cast.

## RC-7 : repli `coalesce` champ par champ, texte FR dans une réponse EN, `'{}'` EN masque le FR

- **Fichier** : `apps/api/src/infrastructure/db/translated.ts:13-14` (utilisé par tous les dépôts).
- **Gravité** : mineur.
- **Défaut** : le repli se fait colonne par colonne, et non ligne par ligne. Deux effets. (a) Quand la ligne EN
  existe et qu'une colonne nullable y vaut `null` (`logo_alt`, `location`, `stack_label`, `image_alt`,
  `picture_alt`, `description`), le texte FR est servi dans la réponse EN. La valeur « absente en anglais » ne peut
  donc pas s'exprimer. (b) Pour `achievements text[] not null default '{}'`, une ligne EN créée sans réalisations
  vaut `'{}'`, qui n'est pas `null` : le repli ne joue pas, et l'EN affiche une liste vide alors que le FR en a
  trois. docs/01 dit « `en` optionnelle avec repli sur `fr` ». Le repli de la ligne entière n'est pas tranché, et
  le comportement mixte n'est documenté nulle part ailleurs que dans le commentaire du helper.
- **Scénario de défaillance** : une traduction EN partielle (cas normal pendant la relecture de
  `docs/traductions-a-relire.md`) produit une page anglaise au texte alternatif français (accessibilité,
  lecteur d'écran en anglais) et une expérience sans réalisations.
- **Reproduction** :
  ```sh
  psqld -c "update experiences_translations set logo_alt = null, achievements = '{}' where locale = 'en'
            and experience_id = (select id from experiences where slug = 'contentsquare')"
  curl -s 'localhost:3512/api/v1/experiences?lang=en'
  # contentsquare : "jobTitle":"Software Engineer", "logo":{"alt":"Logo de Contentsquare"}, "achievements":[]
  ```
- **Proposition** : faire trancher par Julien, puis l'écrire dans docs/01. Option 1, repli ligne par ligne : on
  choisit la ligne EN si elle existe, sinon la FR (`case when en.locale is null then fr.x else en.x end`, une
  seule règle, simple à reproduire en Rust). Option 2, garder le champ par champ, mais traiter `'{}'` comme absent
  (`coalesce(nullif(en.achievements, '{}'), fr.achievements)`) et documenter le mélange de langues. Dans les deux
  cas, un test e2e qui fige le choix.

## RC-9 : runner, un `commit;` dans un fichier casse l'atomicité et bloque les relances

- **Fichier** : `apps/api/src/infrastructure/db/migrations-runner.ts:109-114`.
- **Gravité** : mineur.
- **Défaut** : `tx.unsafe(content)` envoie le fichier en protocole simple. Un `commit;` (ou `begin;`, `rollback;`)
  écrit dans le fichier, par exemple recopié d'un script `psql`, termine la transaction du runner au milieu du
  fichier. Ce qui précède est validé, et l'insertion dans `schema_migrations` n'a pas lieu.
- **Scénario de défaillance** : la migration échoue après le `commit`. La base est à moitié migrée, la version
  n'est pas enregistrée, et chaque relance échoue sur `relation "…" already exists`. Il faut alors une réparation
  manuelle en production.
- **Reproduction** : même script, `0002_commit.sql` =
  `create table t_b (id int); commit; select * from table_inexistante;`. Résultat : échec, `t_b` présente,
  `schema_migrations` = `['0001']`. La relance échoue ensuite sur `relation "t_b" already exists`.
- **Proposition** : `listSqlFiles` ou le runner refusent un fichier qui contient, hors commentaires, une
  instruction de contrôle de transaction (`/^\s*(begin|commit|rollback|start\s+transaction|end)\s*;/im`).
  Documenter la règle dans `db/README.md`, et ajouter un test e2e du refus.

  `profile/drizzle-profile.repository.ts:1,13`).
- **Gravité** : mineur.
- **Défaut** : CLAUDE.md dit « Nest n'apparaît que dans `infrastructure/http` (et dans les modules Nest de
  `config`/`db`) ». Les 11 dépôts importent `@nestjs/common` et reposent sur `design:paramtypes` (métadonnées de
  décorateurs émises par SWC) pour recevoir `DrizzleDatabaseClient` via `useClass`. Les cas d'usage, eux, sont
  câblés par `useFactory`. Le contrôle D8 du backlog ne vérifie que `domain/` et `application/`, donc l'écart passe
  inaperçu.
- **Scénario de défaillance** : un outil de build qui n'émet pas les métadonnées (esbuild, cf. CLAUDE.md) produit
  des dépôts avec `client` `undefined` : 500 sur toutes les routes, sans erreur au démarrage. Les dépôts ne sont
  pas instanciables hors Nest sans connaître cette dépendance implicite.
- **Reproduction** :
  `grep -rln "@nestjs" apps/api/src/infrastructure/db | grep -v database.module.ts` liste 11 fichiers.
- **Proposition** : retirer `@Injectable()` des dépôts. Dans chaque module :
  `{ provide: PROFILE_REPOSITORY, useFactory: (c: DrizzleDatabaseClient) => new DrizzleProfileRepository(c), inject: [DrizzleDatabaseClient] }`
  (même schéma que les cas d'usage). Étendre le grep D8 à `src/infrastructure/db` en excluant
  `database.module.ts`.

## RC-11 : ligne publiée sans traduction `fr`, disparition silencieuse et aucun garde-fou au déploiement

- **Fichiers** : tous les dépôts (`innerJoin(fr, …)`, par ex.
  `apps/api/src/infrastructure/db/experiences/drizzle-experiences.repository.ts:46`) ;
  `apps/api/src/infrastructure/db/seeds-runner.ts:35-42`.
- **Gravité** : mineur.
- **Défaut** : la règle « `fr` obligatoire » n'existe qu'en convention et dans un e2e sur le seed
  (`seeds.e2e-spec.ts:76`). En production, une ligne publiée sans traduction `fr` est écartée par l'`inner join`,
  sans log ni erreur. Pour le profil, le `/cv` entier passe en 404.
- **Scénario de défaillance** : un seed ajoute une expérience et sa seule traduction `en` (copier-coller), puis
  déploie. L'expérience n'apparaît ni en `fr` ni en `en`, et rien ne le signale : ni le runner de seeds, ni l'API,
  ni les logs.
- **Reproduction** :
  ```sh
  psqld <<'SQL'
  insert into experiences (slug, kind, company, date_start) values ('qa-sans-fr', 'employment', 'X', '2027-01-01');
  insert into experiences_translations (experience_id, locale, job_title, summary)
    select id, 'en', 'Job', 'Summary' from experiences where slug = 'qa-sans-fr';
  SQL
  pnpm db:seed   # aucun avertissement
  curl -s 'localhost:3512/api/v1/experiences?lang=en' | grep -c qa-sans-fr   # 0
  ```
- **Proposition** : à la fin de `runSeeds`, dans la même transaction que le dernier seed, une requête de
  contrôle : la même que `seeds.e2e-spec.ts:76`, sur les 10 tables et le profil. Elle lève une erreur si une ligne
  publiée n'a pas de `fr`. Le déploiement s'arrête alors avant `compose up`. Le contrôle est en SQL explicite, donc
  portable en Rust tel quel.

## Points positifs

- Hexagonal propre : `domain/` et `application/` n'importent ni Nest, ni Drizzle, ni Fastify. Les cas d'usage sont des classes pures câblées par `useFactory`.
- Pas de N+1 : chaque liste fait une ou deux requêtes (`inArray` sur les identifiants), et `/cv` répond en 15 à 20 ms à chaud.
- Runner de migrations sérieux : verrou consultatif sur une connexion unique, transaction par fichier, checksum SHA-256, tests e2e de rollback.
- Validation stricte des réponses et filtre RFC 9457 : aucune fuite de pile, et les 5xx sont journalisés avec la `ZodError` complète.
- `schema-matches-db.e2e-spec.ts` confronte Drizzle à `information_schema` : la dérive SQL → Drizzle est impossible sans test rouge.
